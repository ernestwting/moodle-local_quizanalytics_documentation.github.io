Getting Started

The fast path, for anyone who wants a report on screen before reading the rest of this document:

  1. Download Zip. Download the most recent version's zip file from Moodle Marketplace.
  2. Install. Site administration → Plugins → Install plugins → upload the zip of this plugin. It unpacks to a single folder that becomes local/quizanalytics.
  3. Upgrade. Visit Site administration once more. This one step registers the viewing capability, the result caches, both prediction models (disabled), and the 15 minute cache warming scheduled task.
  4. Open a course that has at least one STACK question added directly to a quiz slot (not pulled in only via "random question from category"), with at least one finished attempt. Look for an STACK q-type Analytics entry in the course's secondary navigation, checking inside More if the bar is already full.
  5. You land on Quiz Analytics, the coursewide view. Use the Section: switcher at the top to try Question Analytics and Model Analytics as well.
  6. Try the Download PDF button on whichever view is showing.

That is the whole loop. Chapter 4 walks through what each section actually shows and how to read it; Chapter 3 covers every installation setting in full. The GitHub repo for this plugin can be found here. The repo may contain a version in progress, so it is best to download the newest, stable version from Moodle Marketplace.

2.1 Tested at

Rather than claim unlimited scale, this plugin has been directly benchmarked:

  • A real production course: 38 quizzes, 48,445 finished attempts, 200,000+ responses.
  • A synthetic stress test: 50 quizzes × 1,000 students (50,000 attempts total).

See the project's CHANGELOG.md for the specific timings recorded at each scale, and Chapter 3 for the settings that make a large course practical, including parallel cache warming workers and the on demand background compute safeguard.

2.2 What to expect on larger courses

A course with a handful of STACK quizzes and a few dozen students will feel instant: open Analytics, and the report is simply there. A course with many students, many quizzes, and therefore tens or hundreds of thousands of individual responses is a different amount of work, and it is worth setting expectations honestly rather than pretending scale is free.

  • Where the time actually goes. Every graded response has to be read out of Moodle's own response summary text, parsed field by field, and classified before a single chart or indicator can be drawn from it (see Chapter 5 for exactly what that parsing involves). Model Analytics and Diagnostics Analytics add further work on top: an indicator computed per student or per question, a tree edit distance walked per submission, an ANOVA run per question's seed groups. None of this is wasted work, but it does scale with attempts and responses, not with course count.
  • The first computation on a large course is the slow one, not every visit. Once a result is computed, it is cached, and every subsequent visit reads that cache instead of recomputing from scratch. The practical effect is that only a cold cache (a quiz nobody has viewed recently, or one that just received new attempts) is ever slow; a warm one is instant regardless of how large the course is.

The 38 quiz, 48,445 attempt, 200,000+ response production course and the 50 quiz by 1,000 student synthetic stress test named above are exactly the scale this behaviour was built and measured against, not a hypothetical ceiling. See the project's CHANGELOG.md for the specific timings recorded at each scale, and Section 3.4 for the settings below that keep a large course practical.

2.2.1 How the computation is kept streamlined

None of the mitigation here is exotic: it is ordinary server side engineering applied consistently, so that a teacher opening a report never has to wait on the full computation in real time.

  • Cache warming runs ahead of the teacher. A scheduled task, "Warm STACK q-type Analytics result caches," runs every 15 minutes via Moodle cron and precomputes Quiz Analytics and Question Analytics for every STACK quiz, so a teacher almost always lands on an already warm cache rather than triggering a live computation.
  • Cache invalidation is cheap and precise. Each cache entry is keyed on a lightweight SQL fingerprint (attempt count, latest completion time, and summed grades) rather than a fixed expiry, so a cache stays valid, and free of recomputation, for as long as nothing about the underlying attempts has actually changed.
  • Large courses warm in parallel, not one quiz at a time. The cache warming task can fork several worker processes, auto sized to the server's detected CPU and RAM, so a course with many quizzes warms them concurrently instead of serially.
  • A slow cold request never blocks the browser. If a page is opened before its cache is warm and the computation is estimated to exceed the configured time budget (20 seconds by default), the work is handed to a background task instead of making the teacher's browser wait on it. The page shows "generating in the background" and rechecks itself automatically every 20 seconds until the real report is ready.
  • Everything above runs on the Moodle server itself. There is no external analytics service to queue behind and no network round trip to add latency; speed is purely a function of the Moodle server's own resources, which the "Detected server resources" readout on the settings page is used to auto configure.

Section 3.4 in the next chapter covers every one of these settings, its default, and when it is worth adjusting by hand.
