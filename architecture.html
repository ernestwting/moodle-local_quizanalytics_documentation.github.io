Architecture & Design

7.1 System overview

Data flows in one direction, from Moodle's own database out to whatever renders the final view:

Moodle (PHP)
  ↓ reads quiz_attempts / grades / log events via the question engine, gradelib, logstore_standard_log
Moodle DB
  ↓ classes/quiz/analytics/*.php (Quiz + Question Analytics)
  ↓ classes/stack/analytics/*.php (Model + Diagnostics Analytics)
Plotly.js / KaTeX (client side)  or  TCPDF (server side PDF)
  • No CSV round trip, no external service. classes/quiz/data_fetcher.php reads finished attempts straight out of quiz_attempts through Moodle's own question engine; classes/stack/local/stack_attempt_reader.php does the same for Model Analytics and Diagnostics Analytics.
  • STACK question text is rendered through STACK's own CAS engine (castext2_qa_processor), never read as raw stored questiontext.
  • Every computation is pure PHP: no Python, no external service, no Composer dependency required at runtime.
  • Caching applies only to Quiz Analytics and Question Analytics. Every fetch/compute path is backed by a Moodle MUC cache area, keyed on a cheap SQL fingerprint (attempt count, latest completion time, and summed grades) rather than a fixed time to live.
  • Analytics API integration (Model Analytics only): db/analytics.php registers both prediction models via Moodle core's own analytics manager class, using its update_default_models_for_component() method.

7.2 Why the models are shaped the way they are

Moodle's Analytics API imposes four hard constraints that shaped this plugin's design more than anything else did:

  • Core machine learning backends support binary classification only: a target like "predict a student's final grade" has to become a yes/no question rather than a continuous prediction, unless a custom backend is written.
  • Every indicator must return a float in [−1, 1]: every raw signal this plugin computes has to be normalised and bounded before it can legally become an indicator.
  • Moodle's Analytics API currently supports supervised learning only: detections with no natural ground truth label, like seed bias or PRT branch coverage, cannot become a supervised target at all; they need either a proxy label, a static rule based model, or reframing as descriptive statistics outside the ML pipeline.
  • A model is exactly one target, plus any number of indicators, plus one analyser and one backend; there is no way to smuggle two separate objectives into a single target.

Working through those constraints against the original list of roughly eleven behaviours this plugin set out to detect produced a triage: each behaviour became either the thing being predicted (a target), evidence feeding a prediction (an indicator), or a statistical report kept outside the machine learning pipeline entirely (a diagnostic). Seed bias and PRT branch coverage both landed in that third category: neither has a natural label to predict, and both are perfectly well served by a direct statistical test rather than a trained model dressed up to look like one. That architectural honesty is a deliberate choice, not an oversight.

7.3 Where the plugin came from

Originally developed as a hackathon project in 2024 by Juma Zevick Otieno, this was a simple Streamlit application providing Quiz Analytics. That application can be viewed here. After that, Ernest Ting further developed the application, converting the Streamlit to PHP so it could be used in Moodle. As a result of this conversion, STACK q-type Analytics is the merger of two previously separate plugins that used to be installed independently: the original local_quizanalytics, which handled coursewide comparison and per quiz question analytics, and local_stackanalytics, which contributed the two Analytics API prediction models and the diagnostics dashboard that uses no machine learning at all. They now live under one component name, one capability, and one navigation entry. Chapter 7 has the full account of why the two prediction models are built the way they are, including a research style discussion of why some of the eleven behaviours this plugin originally set out to detect became predictions, some became evidence feeding a prediction, and some became plain statistical reports kept deliberately outside the machine learning pipeline. Each section's computation logic carried over from its own original plugin essentially unchanged: only namespaces, the capability, and the navigation entry points changed to make the merge coherent, since both halves had already been independently built and verified before the merge took place.

7.4 Known, tracked gaps

  • Two Model Analytics indicators are documented simplifications of a more rigorous original design: question difficulty's classical test theory proxy instead of a jointly fit two parameter IRT model, and feedback ineffectiveness's aggregate log odds effect size instead of a paired statistical test done per branch, both because the fuller version needs a batch calibration step the Analytics API's per sample indicator model has no hook for.
  • Concept dependency mapping is an intentional placeholder, not an implemented feature. It is better suited to offline sequence mining work than a live dashboard page.
