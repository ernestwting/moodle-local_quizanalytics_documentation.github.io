STACK q-type Analytics Docs / Chapter 1

Introduction

If you teach with STACK, the CAS powered question type that lets a Moodle quiz mark genuine mathematics rather than pattern matched strings, you already have a great deal of data sitting in your gradebook that you probably never get to look at properly. Every attempt records not just a mark, but which Potential Response Tree (PRT) branch a student's answer landed on, how their input compared to the model answer, and how their performance compares to everyone else who received a differently seeded version of the same question. STACK q-type Analytics turns that raw material into something you can actually read: coursewide comparisons, per question breakdowns, two behavioural prediction models, and a pair of diagnostic reports built specifically for people who write STACK questions rather than just administer them. This is one plugin, not a suite you assemble yourself. Install local_quizanalytics and you get a single "Analytics" entry point in every course, with a section switcher at the top of the page moving between four distinct tools:

SectionWhat it answers
Quiz Analytics"How are my STACK quizzes doing, compared against each other, across the whole course?"
Question Analytics"Inside this one quiz, which questions are students actually struggling with, and what are they typing?"
Model Analytics"Which students might be heading for trouble, and which questions might have a marking problem worth a second look?"
Diagnostics Analytics"Is one randomised version of this question unfairly harder than another, and which parts of my PRT logic has anyone ever actually triggered?"

A design decision worth stating up front, because it shapes everything that follows: every number in this plugin is computed on the Moodle server itself, from data Moodle already owns. There is no separate analytics service, nothing is exported to run through an external model, and nothing is estimated by a black box you cannot inspect. If a figure on screen ever looks surprising, the explanation is meant to be findable: in this documentation, in the "About this model" panel next to the number itself, or in the plugin's own source. Chapter 5 exists specifically to make good on that promise, statistic by statistic.

1.1 What this plugin deliberately is not

  • Not a separate service. There is no analytics server to stand up, no Python process, no job queue. Every computation is plain PHP, running inside the same Moodle request, or the same Moodle cron run, that serves the page. Installing the plugin is the entire installation.
  • Not a black box. Both prediction models ship disabled by default. Until an administrator deliberately reviews and trains one, Model Analytics shows each indicator's live reading: a real number, computed fresh from real attempt data, never a trained prediction dressed up as one.
  • Not a data exporter. Nothing in this plugin makes an outbound network call of any kind. The only way information leaves the server at all is a PDF an authorised teacher explicitly downloads, and it contains exactly the data they were already looking at on screen. Chapter 6 covers this in full.
  • Not a replacement for STACK's own grading. Every response is graded by STACK's own CAS engine, through the same question engine API your quiz already uses. This plugin reads the result of that grading; it never recomputes or second guesses it.

1.2 Where this plugin came from

Originally developed as a hackathon project in 2024 by Juma Zevick Otieno, this was a simple Streamlit application providing Quiz Analytics. That application can be viewed here. After that, Ernest Ting further developed the application, converting the Streamlit to PHP so it could be used in Moodle. As a result of this conversion, STACK q-type Analytics is the merger of two previously separate plugins that used to be installed independently: the original local_quizanalytics, which handled coursewide comparison and per quiz question analytics, and local_stackanalytics, which contributed the two Analytics API prediction models and the diagnostics dashboard that uses no machine learning at all. They now live under one component name, one capability, and one navigation entry. Chapter 7 has the full account of why the two prediction models are built the way they are, including a research style discussion of why some of the eleven behaviours this plugin originally set out to detect became predictions, some became evidence feeding a prediction, and some became plain statistical reports kept deliberately outside the machine learning pipeline.

1.3 Requirements

This plugin has nothing to analyse without the STACK question type (qtype_stack) already installed, so install that first. Beyond that, you need Moodle 4.0 or later and, critically, a working Moodle cron. Cron is not a performance nicety here: cache warming for large courses and the on demand background compute safeguard both depend on it running on schedule. Chapter 3 explains exactly why, and how to verify it.
