Privacy & Security

This chapter documents exactly what this plugin does, and does not do, with student and course data, and reflects a direct audit of the codebase rather than a policy statement written separately from it.

6.1 The short version

No student or course data ever leaves the Moodle server. Every computation runs in plain PHP, in process, reading directly from Moodle's own database. There is no analytics service to call, no telemetry, no third party SDK, and no code path anywhere in this plugin that makes an outbound network request.

6.2 What was checked

A direct audit of every PHP and JavaScript file this plugin owns, excluding vendored third party libraries, found:

  • Zero outbound network calls. No curl_*, no file_get_contents() or fopen() against a URL, no fsockopen, no HTTP client library, and no mail() call anywhere in this plugin's own code.
  • Zero external script or asset loading. Every JavaScript and CSS dependency, including Plotly.js, KaTeX, and TCPDF, is vendored locally inside the plugin, specifically so that no chart, no rendered maths, and no PDF generation step ever needs to reach a CDN.
  • Zero telemetry, analytics, or error reporting integrations. No Sentry, Bugsnag, Google Analytics, Mixpanel, or anything similar; checked directly, never assumed absent.
  • Zero registered Moodle web services. There is no db/services.php and no external function class anywhere in this plugin, so there is no API surface a token or third party integration could pull data through.
  • Zero file storage of exported data. PDF exports stream straight from server memory to the requesting browser via Moodle's own send_file(), never written to Moodle's file storage, never given a public or guessable URL.

The only way data leaves the server at all is a PDF that an authorised user explicitly clicks Download PDF for, and that PDF contains exactly the data they were already looking at on screen.

6.3 Who can see what

Every entry point this plugin exposes requires, in order:

  1. require_login($course): a valid, logged in session.
  2. require_capability('local/quizanalytics:view', $context): a course context capability granted, by default, only to the editing teacher, teacher, and manager roles.

That capability carries RISK_PERSONAL deliberately: this plugin shows individual students' response text, grades, and behavioural indicators across an entire course, and Moodle's own permission system is made to flag that risk level explicitly rather than leave it implicit. Students cannot see this plugin's pages at all. State changing actions are protected by require_sesskey(), Moodle's standard CSRF protection.

6.4 What this plugin stores

Per its own Moodle privacy provider, this plugin stores no personal data of its own: it implements Moodle's null_provider interface:

  • Every response, attempt, grade, and log event it reads comes live from tables Moodle core or qtype_stack already own, already covered by their own privacy providers.
  • The only local storage this plugin uses at all is Moodle's own MUC cache API, and only for Quiz Analytics and Question Analytics. Each cache entry is a disposable, purely derived recomputation, invalidated automatically the moment a relevant attempt changes.
  • Model Analytics's trained predictions, once an administrator enables and trains a model, are stored by Moodle core's own core_analytics component, already covered by core's own privacy provider.

6.5 Anonymise mode: what it does and doesn't do

The Anonymise student data toggle replaces every real student name with a stable pseudonym ("Student 1", "Student 2", …) and every email with student<N>@anonymized.edu, consistently across every table, chart, and PDF derived from that page load. What it's for: sharing a screenshot or PDF without real names visible in it. What it is not: an access control. It is a display layer substitution, computed fresh on every page load from the real underlying data. Anyone who already holds the viewing capability on that course can toggle it back off and see real names.

6.6 Responsible use

Model Analytics and Diagnostics Analytics compute statistical patterns from real behavioural data, worth reading with the same care the plugin's own interface states directly:

These are statistical patterns, not proof of anything. An anomalous response time is a prompt to check in with a student, not evidence of misconduct on its own. Small courses will show noisier and less reliable readings simply because they have fewer data points to work from. Every number here describes what a student did in this course, not who they are.
